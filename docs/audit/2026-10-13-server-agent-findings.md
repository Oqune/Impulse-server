# Impulse Server — read-only audit findings

Дата: 2026-10-13  
Область: Rust server, auth, framing/resource limits, replay/sync/TTL, certificate rotation, Tokio shutdown, logging/privacy, TUI и тестовое покрытие.  
Ограничения проверки: только чтение и статический анализ. Сборки и тесты не запускались по поручению корневого агента. `server/config.toml`, логи, ключи и персональные секреты не читались. Wire v3 и код не изменялись.

## Краткий вывод

Сервер имеет полезные базовые защиты: WebTransport/QUIC с pinning, ограничение размера входящего кадра, ограничение числа сессий, nonce в challenge-response, bounded channel для прямых ответов, in-memory store с TTL и тест реального QUIC/auth/relay/sync пути. Но заявленная готовность к защите и устойчивой эксплуатации пока не подтверждается: есть несколько доступных удалённому клиенту путей к удержанию всех session permits и исчерпанию RAM; штатное завершение dual-stack сервера может зависнуть; ротация сертификата ломает TOFU-клиентов сразу при смене сертификата, несмотря на заявленное окно перекрытия.

## Дефекты

### P1 — ошибки обработки пакета не закрывают сессию

В [session.rs](../../server/src/relay/session.rs#L404) ошибка `process_packet` делает `break` только из внутреннего цикла разбора уже буферизованных пакетов. Внешний цикл чтения продолжается. Handler возвращает ошибку для неаутентифицированных `Data`, `Heartbeat`, `Sync` и `KeyExchange`, неверного Auth и Disconnect ([auth.rs](../../server/src/relay/auth.rs#L187), [auth.rs](../../server/src/relay/auth.rs#L219), [auth.rs](../../server/src/relay/auth.rs#L248), [auth.rs](../../server/src/relay/auth.rs#L298), [auth.rs](../../server/src/relay/auth.rs#L315), [auth.rs](../../server/src/relay/auth.rs#L369)). Поэтому пакет с ошибкой не закрывает соединение.

**Триггер и ущерб:** клиент открывает WebTransport session, не проходит auth и продолжает посылать запрещённые пакеты чаще, чем раз в 300 секунд. Каждый раз reader получает данные и сбрасывает idle timeout, но session permit остаётся занят. До 1024 таких клиентов могут исчерпать весь лимит параллельных сессий и остановить приём легитимных клиентов. `Disconnect` также не завершает сессию, пока клиент отдельно не закроет stream/connection.

**Минимальное исправление:** распространить результат handler наружу из session read loop, чтобы `Err` завершал reader и вызывал существующий `cleanup_session_state`; сохранить мягкий drop только для явно определённых случаев. Не менять формат Wire v3.

**Тест:** реальный loopback WebTransport клиент отправляет неаутентифицированный `Data` (и отдельно неверный Auth/Disconnect), после чего проверяется закрытие соединения, освобождение счётчика сессий/permit и успешное подключение нового клиента.

### P1 — хранилище данных ограничено количеством, но не общим объёмом байтов

`MAX_MESSAGES` равен 10 000, а максимум одного payload — 1 000 000 байт ([storage/mod.rs](../../server/src/storage/mod.rs#L17), [limits.rs](../../server/src/protocol/limits.rs#L3)). `MessageStore::push` клонирует payload в DashMap ([storage/mod.rs](../../server/src/storage/mod.rs#L71)), а аутентифицированный клиент может многократно помещать сообщения в store ([auth.rs](../../server/src/relay/auth.rs#L248), [auth.rs](../../server/src/relay/auth.rs#L272)). Заявленный агрегатный предел 512 MB учитывает только временные stream buffers ([limits.rs](../../server/src/protocol/limits.rs#L12), [session.rs](../../server/src/relay/session.rs#L340)); он не применяется к хранилищу.

**Триггер и ущерб:** аутентифицированный участник быстро отправляет 10 000 сообщений по 1 MB. Store может занять примерно 10 GB без учёта копий при обработке и синхронизации, что позволяет вызвать OOM и перезапуск сервера. Это не ограничивается 512 MB или 72-часовым TTL: заполнение лимита возможно раньше.

**Минимальное исправление:** добавить общий лимит сохраняемых байтов, с учётом освобождения payload при вытеснении и TTL sweep; при достижении лимита явно применить bounded eviction/backpressure. Сохранить лимит count и протокол без изменений.

**Тест:** заполнить хранилище payload максимального размера, подтвердить инвариант `retained_bytes <= configured_cap` после вставок, count eviction и TTL sweep; отдельный тест должен убедиться, что sync не возвращает больше байтов, чем разрешает его лимит.

### P1 — повторные KeyExchange накапливаются без лимита

Каждый аутентифицированный `0x31` копируется в `key_exchange_store[session_key]` через безлимитный `Vec<Vec<u8>>` ([auth.rs](../../server/src/relay/auth.rs#L315), [auth.rs](../../server/src/relay/auth.rs#L323), [auth.rs](../../server/src/relay/auth.rs#L336)). Допустимая длина одного кадра ограничена примерно 1 MB, но количество кадров за время сессии ничем не ограничено. Запись удаляется только при завершении сессии ([session.rs](../../server/src/relay/session.rs#L486)). Активный клиент может поддерживать сессию heartbeat-пакетами и оставлять её открытой дольше idle timeout.

**Триггер и ущерб:** авторизованный клиент многократно отправляет допустимые `0x31`; память растёт до исчерпания RAM. Replay при новой авторизации также клонирует все сохранённые кадры ([auth.rs](../../server/src/relay/auth.rs#L193)).

**Минимальное исправление:** ограничить число и/или сумму байтов сохранённых key exchange на сессию/пользователя и определить поведение при превышении; хранить только актуальный пакет, если это соответствует модели key exchange. Учитывать копии, идущие в replay.

**Тест:** повторять максимальный валидный по длине `0x31` и проверять жёсткую верхнюю границу памяти/числа записей, корректное вытеснение и корректный replay после превышения. Протокол не менять.

### P1 — Sync ограничен числом, но одна выдача может составить около 2 GB

`Sync` запрашивает до 2 000 сообщений ([relay/mod.rs](../../server/src/relay/mod.rs#L55), [auth.rs](../../server/src/relay/auth.rs#L219)), а каждое сообщение может иметь payload до 1 MB. `since` копирует выбранные записи в новый `Vec` ([storage/mod.rs](../../server/src/storage/mod.rs#L104)), после чего encoder строит ещё один большой буфер ответа ([protocol.rs](../../server/src/protocol.rs#L279)). Лимита на байтовый размер SyncResponse нет.

**Триггер и ущерб:** один аутентифицированный клиент с `last_seen_id=0` при заполненном store инициирует сборку ответа размером до ~2 GB, а повторные запросы усиливают CPU/RAM/network pressure. 2 000 сообщений ограничивают count, но не «multi-hundred-MB» верхнюю границу, заявленную в комментарии.

**Минимальное исправление:** считать общий объём ответа и прекращать выбор при достижении byte budget (или вводить меньший лимит count, рассчитанный на максимальный payload); клиент продолжает синхронизацию с ID последнего полученного сообщения. Wire-формат остаётся прежним.

**Тест:** заполнить store максимальными payload и проверить, что кодирование ответа не превышает фиксированный byte cap и последовательные запросы позволяют дочитать все записи без пропусков/дубликатов.

### P1 — заявленное окно ротации сертификата не сохраняет TOFU-связность

При ротации `CertManager` хранит прежний сертификат в `previous` ([cert/mod.rs](../../server/src/cert/mod.rs#L334)), но `DynamicCertResolver` содержит и возвращает только `primary` ([cert/mod.rs](../../server/src/cert/mod.rs#L424), [cert/mod.rs](../../server/src/cert/mod.rs#L445)). Housekeeping сразу заменяет текущий сертификат TLS resolver и только затем отправляет `NewCertHash` подключённым клиентам ([housekeeping.rs](../../server/src/relay/housekeeping.rs#L41), [housekeeping.rs](../../server/src/relay/housekeeping.rs#L68)). `previous` не используется для TLS handshakes. При старте с сертификатом, которому пора ротироваться, генерируется новый, а `previous` остаётся пустым ([cert/mod.rs](../../server/src/cert/mod.rs#L168)).

**Триггер и ущерб:** сразу после плановой ротации новый handshake предъявляет только новый сертификат. Клиент, закрепивший старый fingerprint, но не получивший/не обработавший `NewCertHash` до ротации, не может пройти TLS pinning, чтобы получить этот hash. Перезапуск в окне ротации дополнительно теряет старый сертификат и анонс. Это может навсегда отрезать офлайн-клиента до ручного повторного доверия сертификату. Заявленное перекрытие в 4 дня фактически не действует для TLS pinning.

**Минимальное исправление:** согласовать с клиентским протоколом v3 путь обновления pin до смены сертификата (например, durable/catch-up control с подтверждением клиента либо serving старого fingerprint в допустимой модели pinning). До доказательства сценария нельзя заявлять автоматическую ротацию как непрерывную. Не менять wire v3 несинхронно.

**Тест:** integration тест с двумя закреплёнными клиентами, один из которых offline на момент ротации; проверить, что он может восстановить доверие после возвращения. Добавить тест ротации с live resolver и тест рестарта около порога истечения.

### P1 — завершение dual-stack сервера может зависнуть

В dual-stack режиме `run` ожидает оба accept loop через `tokio::join!` ([relay/mod.rs](../../server/src/relay/mod.rs#L246)). Каждый ждёт `shutdown.notified()` ([relay/mod.rs](../../server/src/relay/mod.rs#L272)), но Ctrl+C, TUI quit и TUI error используют `Notify::notify_one()` ([main.rs](../../server/src/main.rs#L44), [ui/mod.rs](../../server/src/ui/mod.rs#L341), [ui/mod.rs](../../server/src/ui/mod.rs#L467)). `notify_one` пробуждает одного ожидающего; второй loop может остаться заблокированным навсегда, поэтому `join!` и процесс не завершатся.

**Триггер и ущерб:** включён IPv6 endpoint и пользователь отправляет Ctrl+C, нажимает `q` или TUI сигнализирует ошибку. Один accept loop закрывается, второй не получает событие. Поведение особенно заметно при service stop/deploy, где процесс остаётся зависшим.

**Минимальное исправление:** использовать broadcast/cancellation token, который видят все loop'ы, либо каждый loop ожидать общий watch state; обеспечить завершение housekeeping и соединений при отмене. Дополнительно `main.rs` заявляет SIGTERM, но явно устанавливает только `ctrl_c()`; добавить отдельное Unix SIGTERM ожидание.

**Тест:** запускать оба endpoint'а на loopback и проверять, что один сигнал завершает оба accept loop в ограниченный срок; отдельный platform-gated test для SIGTERM.

### P2 — IP-адреса и SAN попадают в логи вопреки privacy policy

Политика разрешает логи размеров, opcodes, session IDs и timestamp ([policies.md](../../server/docs/policies/policies.md#L26)). Реализация пишет remote address и настроенные SAN ([relay/mod.rs](../../server/src/relay/mod.rs#L303), [relay/mod.rs](../../server/src/relay/mod.rs#L367)). `RUST_LOG` по умолчанию равен `debug`, логи пишутся в rolling-файлы на 7 дней ([logging/mod.rs](../../server/src/logging/mod.rs#L79), [logging/mod.rs](../../server/src/logging/mod.rs#L92)).

**Триггер и ущерб:** обычный запуск сохраняет сетевые адреса клиентов в файлы; это раскрывает метаданные участника и нарушает указанное правило приватности. SAN могут содержать внутренние имена хостов/IP.

**Минимальное исправление:** убрать IP и полный SAN из постоянных логов либо явно ограничить их debug-only с безопасной редактировкой адресов; не менять TUI функциональность. Проверить захват логов на событиях connect/rate-limit.

## Документация и пробелы тестового покрытия

- Реальный loopback тест есть в [live_tests.rs](../../server/src/ui/live_tests.rs#L46): pin success/failure, два клиента, auth, heartbeat, broadcast, Sync, reconnect/replay и обычное завершение с одним IPv4 endpoint. Он не проверяет malformed/auth failure eviction, Sync byte bounds, key exchange replay memory bounds, cert rotation, IPv6 shutdown или SIGTERM.
- `tests/multi_client_stress.rs` работает на уровне `MessageStore`, а не с relay/session/network. Комментарии про per-recipient isolation не соответствуют фактической серверной модели: сервер хранит opaque blobs и рассылает их подключённым клиентам; выбор получателя выполняется на клиентах. Этот тест не подтверждает сетевую изоляцию получателей и не является нагрузочным тестом.
- Тестов со стрессом реального WebTransport и измерением предельной памяти/throughput в репозитории не обнаружено. Имеющийся QUIC test можно запустить отдельно корневому агенту: `cargo test live_pinned_quic_auth_heartbeat_relay_and_sync -- --nocapture`; обычные серверные проверки: `cargo test`, затем `cargo clippy --all-targets -- -D warnings`. Я их не запускал.
- README явно классифицирует сервер как research prototype, предупреждает, что гибридный post-quantum TLS в runtime не верифицирован, и что server видит routing metadata/timing ([README.md](../../server/README.md#L22)). Поэтому подтверждение PQ-защиты или пригодности для высоконадёжного/критически важного deployment на основе текущей серверной кодовой базы невозможно.
- Документация дрейфует: root AGENTS описывает server TTL как 24 ч, фактический `MESSAGE_TTL` и README дают 72 ч; английский README описывает 4-дневное перекрытие, русская версия местами — 2 дня, а TLS resolver не обслуживает оба отпечатка. Также root AGENTS указывает server v3.0.x, `Cargo.toml` — 3.1.0. Эти расхождения стоит согласовать до выпуска.

## Локальный запуск с Android Emulator и проверки

Для Android Studio Emulator адрес хоста обычно `10.0.2.2`; сервер должен слушать интерфейс, доступный эмулятору (например, `0.0.0.0:4433`), UDP 4433 должен быть разрешён Windows Firewall. В сертификат нужно включить SAN `10.0.2.2`, а клиенту передать fingerprint через штатный TOFU/QR flow. Для физического устройства вместо `10.0.2.2` используется LAN IPv4 компьютера и соответствующий SAN. Не публиковать парольный Argon2 hash, приватный PEM или содержимое локального config в командном выводе/отчётах.

Для быстрого end-to-end smoke запускается именованный тест выше; он создаёт временный сертификат и слушает loopback/эпhemeral port, поэтому его можно использовать как проверку реального QUIC пути без внешней сети. Это функциональный smoke, не throughput test.

Нагрузочного инструмента или отдельного сетевого load-test скрипта в `server/scripts`/`server/tests` не обнаружено. Для защищённого профиля проверки стоит добавить ограниченный тестовый QUIC harness, который отправляет валидные максимальные Data и KeyExchange кадры, конкурирующие Sync-запросы и незавершённые/ошибочные сессии; измерять retained bytes, RSS, число активных permits, задержки и поведение после лимита. Использовать только loopback/изолированную тестовую сеть, с верхней границей клиентов, длительности и объёма.

## Ограничения дизайна, а не дефекты

- Сервер является opaque relay и по дизайну не расшифровывает и не интерпретирует payload `0x31`/`0x32`; любые утверждения о криптографической валидности содержимого должны подтверждаться клиентом.
- Внешние sender/recipient identifiers, timing и факт broadcast видимы серверу; это прямо отражено в README и требует соответствующей модели угроз.
- Сервер использует короткоживущий самоподписанный ECDSA P-256 сертификат с TOFU; это не CA PKI и не доказывает post-quantum аутентификацию. README отдельно помечает runtime PQ TLS как непроверенный.
- Store эфемерен: перезапуск теряет сообщения, а TTL сам по себе не означает durable delivery.
